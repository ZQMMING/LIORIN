## 2. 根本障碍：两仓顶层包名冲突（这是真正的卡点）

| 仓 | `pyproject.toml` name | `src/` 布局 |
|---|---|---|
| 主仓 | `tongshu` | `src/tongshu/{api,engines,facts,reasoning,spec,signal,…}` |
| 河洛包 | `heluo-engine` | `src/tongshu/{engines,facts,reasoning,spec}` |

**两仓的顶层包名都是 `tongshu`**，且 `engines / facts / reasoning / spec`
**四个子包同名重叠**。

实测（把两仓 `src` 同时放进 `sys.path`）：
```
from tongshu.engines.heluo.canonical_signals import build_platform_signals
→ ModuleNotFoundError: No module named 'tongshu.engines.heluo.canonical_signals'
```
原因：`sys.path` 里**只能有一个** `tongshu` 包被解析到 —— Python 取
`sys.path` 中**第一个**匹配项的 `tongshu/__init__.py`，
其 `__path__` 指向**单一目录**，不会跨两个 `src/` 拼接。
故两个 `tongshu` **不能同时 import**。

⚠ 这也解释了主仓 `engines/heluo/` 为何只剩一个 `frozen_state.py`：
它是拆包时留下的「同名不同源」残骸 —— 主仓 import 它时拿到的是
**主仓自己的** `tongshu` 命名空间下的那个文件，不是河洛包的。

### 2.1 ★ 实测：两个 `tongshu` 会**互相吃掉对方**（静默破坏，非报错）

把两仓的 `src/tongshu` 分别放进 `sys.path` 的两个位置，实测：

| 场景 | `tongshu.__path__` | 主仓 `signal.normalizer` | 河洛 `engines.heluo.canonical_signals` |
|---|---|---|---|
| 主仓 src 在前（主仓 editable 安装态） | 主仓的 | ✅ 可 import | ❌ **ModuleNotFoundError** |
| site-packages 在前（主仓非 editable + 河洛包装了） | **河洛包的** | ❌ **ModuleNotFoundError: No module named 'tongshu.signal'** | ✅ 可 import |

⚠ **后一行是主仓整体瘫掉**：主仓 32 个顶层子包（api / signal / pipeline_stages /
db / render …）**全部消失**，且报错信息只说「找不到 tongshu.signal」，
**不会提示「你装了河洛包」** —— 这是典型的静默破坏。

⇒ **路径 A（主仓 pip install 河洛包）在现状下会炸主仓**，
除非河洛包先改顶层包名（`tongshu` → `heluo_engine`）。

⇒ 河洛包**当前形态不可被主仓直接 pip 安装**。
本包 `pyproject.toml` 的 `name = "heluo-engine"` 与实际安装出的顶层包名
`tongshu` **不一致** —— 装了会覆盖同名 `tongshu`，不装则主仓用不了。
**这是河洛包自身的打包缺陷，应在河洛域内修**（见 §5 路径 A 第 0 步）。

## 3. 平台侧另有两处硬缺口（独立于包名冲突）

### 3.1 `gua_yao_map` 只映射乾/坤 ⇒ 其余 62 卦 → UNKNOWN

实测 `signal/normalizer.py:137-143` 的 map 键 = `['乾', '坤']`。
`normalize_heluo` 找不到卦即返回
`NormalizationResult(status=UNKNOWN, rejection_reason="Heluo gua '<卦>' not mapped")`。
⇒ 河洛产出的信号里，**只有先天卦为乾/坤的能过**，其余全被拒。

### 3.2 方向判定用**全等**匹配 ⇒ 恒不命中

`signal/normalizer.py:164-172`：
```python
positive_shi = {'吉', '亨', '利'}
negative_shi = {'凶', '不利', '吝'}
if shi in positive_shi:  direction = 'POSITIVE'
elif shi in negative_shi: direction = 'NEGATIVE'
else: direction = 'NEUTRAL'
```
但河洛产出的 `shi` 是**长文本**（实测 82–141 字，如
「厥孚交如，威如，吉。；元数有归，兼卦叶吉，为贵人有光明盛大之德…」）。
⇒ 实测 **4 条信号 0 条命中**，方向恒为 NEUTRAL。

### 3.3 但 3.1 **不能由河洛侧补表**

「64 卦 × 6 爻 → 平台 17 类事件本体」的映射，**原典没有**：
`EVENT_TYPE_BY_ID` 的 17 类（CAREER/FAMILY/EDUCATION/LIFE_EVENT 四域）
是**平台的 ontology**，不是《河洛真数》的概念；
检索原典未见「某卦某爻主某事」的对应表。

用判词层关键词反推也不可靠 —— 实测 384 爻中：
每爻命中候选事件 **0 类 60 爻 / 1 类 97 / 2 类 101 / 3 类 71 / 4 类 35 /
5 类 12 / 6 类 3 / 7 类 4 / 8 类 1**，**多重命中无法唯一定位**，
且 60 爻零命中。⇒ **不能据此造表**（属臆造，违反「不凭猜补规则」）。

⇒ 3.1 的正解是**由平台侧责任方裁定**：
  (a) 按平台 ontology 补全 64 卦映射（需用户/平台 owner 拍板，**非河洛能决定**）；
  (b) 或改为**不按卦映射**（如按「叶吉/不叶 + 域」聚合），避免逐卦表。
  无论 (a) 还是 (b)，**都在主仓侧**，河洛域内无对应改动。

## 4. 三条可行路径

### 路径 A：主仓消费「已发布的河洛包」（推荐）

1. 河洛包以 `heluo-engine` 名义发布（PyPI 或 git URL 依赖）；
2. 主仓 `pyproject.toml` 加依赖；
3. 主仓 import 改为 `from heluo_engine.…`（**需河洛包改顶层包名**
   或提供 `heluo_engine` 顶层别名）；
4. `compute_stage` 恢复调用；`signal_engine.build()` 调
   `build_platform_signals(result)`；平台侧修 3.1 / 3.2。

**代价**：河洛包顶层包名要改（`tongshu` → `heluo_engine` 或
`heluo.engine`），是**破坏性**改动 ⇒ 河洛包内所有
`from ..xxx import` 相对导入、以及 `tests/` 的 `sys.path` 注入都要同步改。
**收益**：两仓彻底解耦，主仓 pip 装河洛包即可用，无源码冲突。

### 路径 B：河洛包并入主仓（回到拆包前）

1. 河洛包分支的 `src/tongshu/**` 合入主仓 `src/tongshu/**`；
2. 主仓 `compute_stage` 恢复调用 + 修 3.1 / 3.2。

**代价**：放弃「独立包」这层封装（当初提纯的目的）；
主仓 `engines/heluo/` 需从残留的 1 个文件恢复为完整包。
**收益**：零命名空间问题，改动量最小，历史上已验证可跑（2026-09 全链路 PASS）。

### 路径 C：主仓以「子进程/服务」消费河洛包

主仓不 import 河洛包，改由独立进程跑河洛包、交换结构化 JSON。

**代价**：多一层 IPC，性能与运维成本上升。
**收益**：完全解耦，适合河洛包继续独立演进。
**适用**：若河洛包还要独立发布、独立版本化。

## 5. 推荐

**路径 B（并入主仓）** —— 理由（**全部经实测**）：

### 5.1 河洛包不是「独立项目」，而是**主仓的分裂副本**

两仓 `src/tongshu/**` 逐文件比对（按**相对路径**精确比，非 basename）：

| 类别 | 数量 | 说明 |
|---|---|---|
| 相对路径相同 + **内容逐字相同** | **24 个** | 合并零风险（`engines/time/*`、`engines/yi/*`、`spec/canonical/*`、`bazi_ten_gods.py`…） |
| 相对路径相同 + **内容有差异**（真冲突） | **5 个** | 见 §5.2 |
| **仅河洛有**（合并即新增） | **37 个** | `engines/heluo/**` 35 个 + `engines/heluo_adapter.py` + `engines/heluo/relationship/engine.py` —— 正是河洛域主体 |
| 仅主仓有 | 333 个 | 合并时**保留不动**（紫微/黄历/禄命/盲派/平台层…） |

且两仓 `src/tongshu/__init__.py` **逐字相同**（都是
`"""TONGSHU reasoning pipeline v1.0."""` + `__version__ = "1.0.0"`）
⇒ **河洛本就是主仓的一部分**，2026-10-16「独立包提纯」是**复制出去**而非真拆仓。

### 5.2 真冲突只有 5 个（合并须逐个处理）

| 文件 | 河洛 | 主仓 | 性质 |
|---|---|---|---|
| `engines/__init__.py` | 1254B | 359B | **河洛版是主仓版的超集**（河洛版导出 Ziwei/Huangli/Bazi 三引擎，主仓版只导出一部分）⇒ 取河洛版 |
| `engines/heluo/frozen_state.py` | 11871B | 9693B | **河洛域文件** ⇒ 取河洛版（河洛包本轮三轮修复的成果） |
| `engines/time/jd_converter.py` | 5150B | 2724B | **历法口径**：河洛版含儒略历修法（1582 年前），主仓版是旧的 ⇒ **已裁定（2026-10-24）：取儒略历版**，见下方「历法口径裁定记录」 |

### 5.2.1 历法口径裁定记录（2026-10-24，已裁定）

**裁定：取儒略历版**（`jd < 2299160.5` 走儒略历路径，之后沿用原实现）。

**依据（不是推理，是实测 + 已有的独立实现）**：

1. **原典硬算例**：1206-11-30 21:00，《河洛真数》L186 作
   「丙寅 庚子 丙子 己亥」（子月）。修前判成「丙寅 **己亥** 丙子 己亥」（亥月）。
   修后 ✅ 逐字吻合原典。
2. **与 sxtwl 同口径**：sxtwl 内部（`JD2DD`/`fromSolar`/`getDayGZ`/`getMonthGZ`）
   对 1582-10-15 之前一律用**儒略历**；1206 年大雪实测
   —— 修前标 `1206-12-07 09:34`，修后标 `1206-11-30 09:34`，
   与 `sxtwl.JD2DD` **逐分钟一致**（相差 7 天）。
3. **影响面**：1582-10-16 ~ 2200-12-31 共 **225,797 天**逐日核对 → **0 天差异**
   （现代日期零风险）；1900-2100 抽样 5904 组四柱 → **0 处差异**；
   古日期抽样 1100-1582 共 11,011 组 → 年/月柱变 1320 处（12%，全在交节窗口内）、
   日柱/时柱 **0 处**变化、另 158 处由「直接抛 `No '节' found within 33 days`」变为正常出盘。
4. **已有独立实现**：八字 owner 已在分支 `fix/bazi-julian-caliber-20261022`
   （commit `6fe1326d`，2026-10-22）落地**逐字相同**的修法 ——
   本裁定是**采纳既有裁决**，不是河洛单方面主张。

**三处已统一**（2026-10-24 实测 md5 逐字一致）：

| 位置 | 状态 |
|---|---|
| 河洛包 `heluo_engine/engines/time/jd_converter.py` | ✅ 儒略历版 |
| 八字分支 `fix/bazi-julian-caliber-20261022`（`6fe1326d`） | ✅ 儒略历版 |
| 主仓 trunk `origin/main` | ⏳ **本次以 `fix/jd-converter-julian-caliber-20261024` 分支落地**（原为旧的 proleptic Gregorian 版，被 `bazi_engine.py` 生产引用） |

守卫：`tests/test_jd_converter_calendar_caliber.py`（河洛包与主仓各一份，5 项：
改历前与 sxtwl 同口径 / 改历后逐字节不变 / 改历点连续性 / 日柱时柱不受影响 /
原典 L186 算例月柱归位）。

### 5.3 路径 A 的代价被实测放大

若走路径 A（主仓 pip install 河洛包）：
1. **必须**先改河洛包顶层包名 `tongshu` → `heluo_engine`

## 9. 实际落地记录（2026-10-24 晚间，User 拍板后执行）

§5 推荐的「路径 B」有两种可执行形态，**User 拍板取「vendor 形态」**：

| 项 | 决策 | 理由 |
|---|---|---|
| Q1 主仓是否依赖外部包 | **不依赖外部包**，改为 vendor：主仓内放 `src/heluo_engine/`（与 `src/tongshu/` **平级**） | 与其它引擎一致 + 单仓自包含 + 可独立部署到服务器；主仓 `[tool.setuptools.packages.find] where=["src"]` **自动**纳入打包 |

### 9.1 旧副本勘察结论（实测，逐文件）

* 旧副本 **29 个 .py**；独立包 70 个。
* 逐个 basename 比对：**旧副本无一独有能力**；独立包在同名文件上**普遍更新**。
* 旧副本**无资源目录**（`data/` `orig/` `docs/` 全在独立包内）。
* 主仓下游 import 旧副本仅 **8 处 / 5 个文件**：
  `engines/heluo_adapter.py`(2)、`engines/heluo_yi_flow.py`(1)、
  `pipeline_stages/compute_stage.py`(1)、`services/daily_state_service.py`(4)、
  `engines/end_to_end.py`(1) ⇒ 全部改指 `heluo_engine.engines.heluo.*`（42 个文件）。

### 9.2 ★ 契约层「字节相同 ≠ 类身份相同」（本轮实测发现的真陷阱）

主仓曾同时存在两份**逐字节完全相同**的契约定义：
`tongshu/spec/canonical/` 与 `heluo_engine/spec/canonical/`（各 5 个文件）。

Python 中两份源码各自定义同名 dataclass ⇒ 得到的是**两个互不相等、
互相不可 `isinstance` 的类**。后果：

* 河洛引擎产出的 `EngineEvidence` 传进主仓契约层时，
  `isinstance(x, EngineEvidence)` 恒为 **False**；
* 平台侧 `assert isinstance(..., CanonicalAssertion)` 一类校验必然变红。

实测受影响断言：`tests/heluo/test_h12_diagnosis.py` 的
`test_assertions_have_required_fields` / `test_judgment_authorized` 两条。

**处置**：主仓 `tongshu/spec/canonical/{__init__,engine_evidence,semantic_atom,
assertion,judgment}.py` 改为**纯转发**（从 `heluo_engine.spec.canonical` 转出），
实体定义只保留一份；子模块路径 `tongshu.spec.canonical.assertion` 等**保持可用**
（既有直接子模块 import 不断）。实测：7 个类身份全统一、跨包 `isinstance` 成立、
子模块路径兼容。

⇒ **可迁移教训**：凡「同一份定义在两处存在」，必须查**类身份**（`is`）而非
**字节**（`md5`）；字节相同只是必要条件。

### 9.3 主仓 adapter 升级到独立包同代

主仓 `src/tongshu/engines/heluo_adapter.py` 此前停留在旧副本（139 行），
落后独立包（238 行）一整代，缺四项能力。升级后：

| 能力 | 旧（主仓旧副本） | 新（与独立包同代） |

| 解卦层失败 | `except Exception: pass` ⇒ **静默无痕** | 挂 `{"error": ...}`，错误**显形**（不阻塞主链） |
| 解读层挂载 | 无 | `interpretation_pipeline.build_interpretation()` 六模块进入生产链 |

⚠ 新逻辑一律**从独立包 import**（`resolve_target_date` / `now_beijing` /
