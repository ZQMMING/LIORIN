## ① 流日层改按需化

**问题**：`_build_timeline` 对 93 流年 × 12 月 = 1,116 个月逐月调
`compute_liuri`，每次 6 次 `_lines_to_hexagram` 卦名换算（合计 **6,696 次**）；
而消费方 guajie 每次排盘只查**一个**月。

此前被 `test_heluo_context.py:91` 的 `len(days)==6` 挡住——实为误判，
该断言只检查段数，不检查日段内容。

**改法**：
- 新增 `compute_liuri_stub(yue_lines, yue_yao_index)`：每段保留
  segment/day_from/day_to/flip_index/lines，**去掉 name/upper/lower**
  三个卦名字符串。
- 新增 `materialize_month_days(month)`：guajie 命中那一个月才现算完整日段。
  放在 `timeline_yun` 而非 `canonical`，避免 guajie 反向依赖 canonical。
- `flip_index` 改用闭式 `(yue_yao_index + 1 + k) % 6`，不再逐段 diff。

**保留 `lines` 是刻意取舍**：`_flip_line` 只复制一个 6 元 list 并翻转一爻，
近乎零成本；而 `TestLazyLiuShi` 两项断言直接读 `d["lines"]`。
保留它即可在**不改任何既有测试**的前提下拿到收益。
（实验：连 `lines` 一起去掉可再省，但需改 2 项既有测试，不取。）

**等价性验证（先验证后改码）**：3 盘 3,432 个月 20,592 个日段，
闭式与「逐爻 diff 求唯一差异爻」**0 处不一致**，且每段 diff 恒恰好一爻。

**实测（同条件 A/B，git stash 对照，15 次取中位）**：

| | 基线 | 按需化后 | 收益 |
|---|---|---|---|
| 算卦耗时中位 | 22.6 ms | **9.1 ms** | **−60%** |
| 算卦耗时 min | 20.7 ms | 7.8 ms | |
| JSON 载荷 | 1173 KB | **890 KB** | **−24%** |
| 月份/日段计数 | 1116 / 6696 | 1116 / 6696 | 不变 |

口径不变：抽样 96 个月 × 6 段逐字段对拍 **0 处不一致**。

## ② 参评诗断接入生产链路

**问题**：`canping.py` 有完整的金锁银匙歌起数算法、有逐页转录的五行部
诗断语料（156 条）、有按层取句的 `layer_lines_448`——但**两端从未接起来**。
`qishu()` 算出的总数不回查诗断表，前几轮校订的 448 语料
在生产链路中拿不到任何一条断语（canping 全模块零调用）。

**接法**：
- `lookup_by_number(number, part)`：join key 即起数得出的四位数
  （原文「二千五百四十二」→ 2542）。
- `judge_canping(day_zhi, hour_zhi, year_gan, year_zhi, gender)`：
  起数 → 查表 → 按性别取本命层两句。层位按参评例
  「上层男命、中层女命、下层男女相共大运流年」，复用 `CANPING_LAYER_SPANS`。
  未收录的数返回 `found=False` + 说明，**不算错误**（全表仍在逐页录入）。
- guajie 新增 `canping` 字段（独立降级 try），起数五步写入 evidence，
  两句断语写入 summary。

**准确性锚点（原典复算，非自证）**——三个向量**全部一致**：

| 原典例 | 起数 | 实测 |
|---|---|---|
| 戌日寅时 乙卯(水) 顺 | 2000+500+14+27+1 = **2542** ✓ | 2542 |
| 申日申时 戊午(火) 顺 | 2000+1300+18+27+2 = **3347** ✓ | 3347 |
| 戌日寅时 乙卯(水) 逆 | 2000+900+14+27+1 = **2942** ✓ | 2942 |

语料检索：3306 → 金部 p59，三层句齐出。

端到端（1990-05-20 辰日申时，男，庚午年纳音土）：
起数 2569 → 土部 p84 → 男命层「珠履騰空去／一雙鳬上天」。

## ③ 清除伪计算

### a. `interpretation._compute_evidence_closure`

原 `return 0.85`（注释「简化版」）。该值被 `_compute_confidence` 以
**0.6 权重**采信 → **任何命盘的置信度都被这一个常数锚定**。

现按输入真实存在的证据字典逐字段统计填充率：
`line_position` / `time_state` / `element_state`。
退化值（None / 空串 / 全 0 数值）视为未填充。
**bool 是 int 子类，`False` 属合法取值**（如 `true_solar_time=False`），
不可按 falsy 剔除——此点由新增测试当场逮到并修正。

### b. `hexagram_state.get_base_factors`

原注释「从 hexagram_state_definitions 表读取」，但**该表全仓不存在**
（已检索 `backend/data` 与 `data`）。与此前修过的 EVENT_TOPIC 求值器
同属「指向幻影资源」。已改为据实陈述为**暂定基准因子**，
并注明 `hexagram` 参数当前未被使用（不同卦返回同一组因子）。
**取值行为不变**，仅更正声明。

## ④ Timeline 三处名实不符

- `daily_hexagram` 注释写「今日卦」，实际存**先天卦**，
  且 `date` 塞的是 `str(birth_year)`（如 `"1990"`）——既非日期也非流日卦。
- `monthly_hexagrams` 恒 `[]`、`hourly_hexagram` 恒 `None`。

三者全仓零消费方（测试里的同名 `daily_hexagram` 均为黄历字段）。
已一律置空并就地注明「真实流月/流日/流时卦在四层时间轴内按需产出」。

**置空的是重复且名不副实的副本，不是删能力**——
新增测试专门验证四层轴内的流月/流日仍完整（12 月 × 6 段）。
