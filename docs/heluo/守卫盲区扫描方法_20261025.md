# 守卫盲区扫描方法（变异测试，2026-10-25）

> 目的：回答「**每次测试还有缺陷？能一次把全部缺陷跑出来吗？**」
> 结论：**不能跑出「全部」缺陷**（缺陷空间无限），但可以**系统性地挖到当前手段的极限**，
> 并把「哪些是真空盲区」一次性列清。本文就是这套方法。

## 一、为什么以前「每次还有新缺陷」

以前的做法是**按需发现**：看到一个问题就查一个、修一个。
⇒ 这是**抽样**，不是扫描 ⇒ 必然反复漏。

真正能收敛的做法是**主动注入缺陷**，看守卫能抓到几个：

* 注入的缺陷被守卫抓到 ⇒ 守卫**有效**；
* 注入的缺陷**存活**（测试仍全绿）⇒ **守卫盲区**。

这叫**变异测试**（mutation testing）。

## 二、仓内已有的做法（及其局限）

`tools/heluo/mutation_verify_*.py` 共 **11 个手工脚本**，每个只挑 2~6 条变异。

| 局限 | 说明 |
|---|---|
| **变异是人挑的** | 挑不到想不到的盲区（如「条件写反」「下界差一」） |
| **覆盖面窄** | 11 个脚本 × 4 条 ≈ 40 条，而自动生成可达 **1163 条** |
| **每个脚本一套流程** | 11 份重复的「注入→跑→还原→校验」代码 |

## 三、本轮新增：自动化扫描（`tools/heluo/mutation_sweep.py`）

### 3.1 自动生成变异（AST 级）

对每个源文件解析 AST，机械地产生四类变异：

| 算子 | 例 | 模拟的现实错误 |
|---|---|---|
| `literal` | `0 → 1`、`True → False`、字符串改一个字 | 阈值写错、常量写错、**原典引用抄错字** |
| `op` | `+ → -`、`< → <=`、`== → !=` | 边界差一、比较反了 |
| `drop not` | `not X` → `X` | 否定漏了 |
| `return→None` | `return X` → `return None` | **返回值被吞掉**（最危险的一类） |

⚠ **只变异可执行代码**：跳过注释与 docstring（注释里的字面量改动不改变行为，
必然「存活」⇒ 全是噪音）。

### 3.2 两级筛（快 → 准）

每条变异都跑全量测试要 ~5 秒 ⇒ 1163 条要 1.6 小时。
故分两级：

1. **快筛**：只跑「与被测模块相关的守卫文件」（≤3 个）；
2. **慢速确认**：快筛放过的再跑全量。

⚠ **超时预算按基线实测耗时定**（`slow = max(120s, 基线×4)`、
`fast = max(60s, 基线×3)`），不拍脑袋。拍脑袋的两种错法：

* 预算过小 ⇒ **基线自己就超时** ⇒ 全部变异被误判成「挂起」；
* 预算过大 ⇒ 真挂起的变异要等很久才判死 ⇒ 扫描慢到跑不完。

⚠ **超时 ≠ 被抓住**（2026-10-25 加固）：把超时直接算成「守卫抓住了」
会**掩盖真盲区** —— 因为守卫文件**本身**慢也会超时。
故分三态：

| 现象 | 判定 | 依据 |
|---|---|---|
| 子进程超时 | **挂起型**（非盲区） | 引擎被变异逼进死循环 |
| pytest 失败（非超时） | **被抓住** | 断言真的红了 |
| pytest 失败但输出带 timeout 痕迹 | **升级慢筛复核** | 可能是守卫本身慢 |

⚠ 慢筛预算刻意 **≥120s**：本仓 `pytest addopts` 里有 `--timeout=60`，
真挂起的变异会在 60s 处被 pytest-timeout 判失败 ⇒ 拿到的是
「pytest 返回 rc≠0」这个**干净结论**；若 subprocess 预算比 60s 小，
subprocess 会先超时 ⇒ 反而丢掉这个有价值的信息。

### 3.3 ★ 关键：区分「等价变异」与「真盲区」

**存活 ≠ 盲区**。本仓大量防御性代码（如 `return ("", "")` 兜底）被变异后
**行为完全不变** ⇒ 那是**等价变异**，不是缺陷。

故引入**行为快照**（`tools/heluo/behaviour_snapshot.py`）：
对 5 个固定盘（男/女、纯卦/杂卦、不同流月流日）产出确定性 JSON，
对比基线与变异后的快照：

* 快照**相同** ⇒ **等价变异**（不是盲区，不必修）；
* 快照**不同** ⇒ **★真盲区**：行为变了，却没有任何守卫发现。

#### ⚠⚠ 快照的三个前提（缺一不可，2026-10-26 实测全部踩过）

**① 快照必须「确定性」**

若快照非确定，则基线快照与变异快照**永远不同**
⇒ **所有存活变异都被误判成真盲区** ⇒ 盲区清单全是噪音。

⚠ 实测踩过：`yuan_qi.py` 的证据文本里插值了一个 Python `set`：

```python
evidence.append(f"先天/后天卦含元气卦: {has_qi}（{all_trigrams}）")
```

而 set 的字符串表示顺序依赖 **PYTHONHASHSEED**（每进程随机）
⇒ 同一盘排两次，卦名顺序就不同 ⇒ 快照非确定。

这**不只是工具问题**，同时是**生产缺陷**：证据文本是**审计留痕**，
不可复现的留痕无法用于回归比对。
⇒ 修法：一律 `sorted()` 后再拼（同类修法见 `hua_gong.py` 的 `sorted(zhengti)`）。
⇒ 守卫：`tests/heluo/test_heluo_snapshot_determinism.py`
（**跨进程**跑两次逐字段比对 —— 必须跨进程，否则哈希种子相同检不出来）。

**② 快照必须「覆盖面足够」**

若某模块的产出**不在**快照里 ⇒ 该模块的变异会让快照输出**不变**
⇒ 被误判成「等价变异」⇒ **真盲区被静默掩盖**。

⚠ 实测踩过：`frozen_state` 的 `FrozenHeluoState` 压根没进快照
⇒ 它的 3 条变异（`return → None`）全被误判成「等价」。

⇒ 快照现已覆盖 `HeluoResult` 的**全部主要输出面**：
数值（numbers）/ 元气（yuan_qi）/ 世代（era）/ 节候（seasonal）/
卦象结构（structure）/ 运程（timeline）/ 判词（guajie）/
解读层（interpretation）/ 冻结状态（frozen_state）/ 时间层判定。

⇒ 守卫同文件：`test_snapshot_covers_main_output_surfaces`
（缺哪个输出面 ⇒ 直接点名）。

**③ 快照必须「快」**

快照每条变异都要跑一次（存活变异的判定依赖它）⇒ 太慢就等于没做。
实测 5 个盘约 8～10 秒 ⇒ 可接受。

#### 快照与守卫的关系（一句话）

> **快照是「盲区的测量仪」，不是「守卫」。**
> 守卫决定「行为变了会不会被发现」，快照决定「行为到底变了没有」。
> ⇒ 快照不准（不确定 / 覆盖不足） ⇒ 盲区判定失效。

### 3.4 工程约束（继承已有脚本的教训）

1. **绝不改测试文件** —— 只改被测源码。否则守卫自身被改坏，
   自验证失效（2026-10-25 实测踩过：prune 同时改了 tests/，
   守卫被改坏 ⇒ 工具以为全绿 ⇒ 静默破坏）。
2. **隔离字节码缓存** —— `PYTHONPYCACHEPREFIX` 指向临时目录，
   否则 `.pyc` 复用会让「还原后复跑」拿到旧字节码 ⇒ 假绿。
3. **还原必须校验哈希** —— 每条变异还原后校验内容哈希，确保真的回到初始字节。
4. **日志写文件** —— 管道会缓冲 stdout，进度看不见。
5. **⚠ 中断必还原**（2026-10-25 加固）—— 扫描是**原地改 `src/`** 的，
   一旦被 Ctrl-C / 被杀 / 抛异常 ⇒ 源码**残留变异**，
   而残留的变异可能恰好让测试绿 ⇒ **下一个使用者拿到的是被污染的源码**。

   实测踩过：手动取消扫描后 `time_layer_judgment._yao_ci_from_guajie`
   残留了 `return None`（原为 `return ("", "")`）⇒ 靠 `git diff` 才抓到。

   ⇒ 故注册 **`finally` + 信号处理器**（SIGINT / SIGTERM / SIGBREAK），
   **无条件还原**并二次校验哈希。

6. **一次只跑一个扫描进程** —— 两个进程同时跑会互相污染
   （A 还原源码时 B 正在变异）⇒ 结果全错。
7. **扫描期间不提交** —— 残留变异会让 `git status` 变脏，
   pre-push 检查会拦下来（这正好是第二道保险）。
8. **⚠⚠ 取快照必须在还原之前**（2026-10-26 修正，**致命顺序错误**）——
   见 3.5 节。

### 3.5 ★★ 最隐蔽的一类错误：工具自己坏了，却报告"一切正常"

#### 3.5.1 实测踩过：先还原、后取快照 ⇒ 真盲区被**系统性掩盖**

2026-10-26 的复核扫描里出现了「杀 327 / 真盲区 0」的结果，
但**这个 0 是假的**。根因是扫描器里的两行代码**顺序错了**：

```python
rc, out = runner.run_tests(cache, timeout=slow_timeout)
runner.restore()                      # ← 先还原源码
if rc == 0:
    mut_snap = _behaviour_snapshot(cache)   # ← 后取快照（读到的已是原码！）
```

快照子进程读的是**磁盘上的源码** ⇒ 此时已被还原 ⇒
快照**必然**等于基线 ⇒ **每一个存活变异都被判成「等价变异」**
⇒ **真盲区一个都发现不了**，而报告却写「★ 真盲区 0」。

⚠ **为什么两轮扫描都没发现它**：因为它**不产生任何报错**——
扫描器正常退出、还原校验通过、日志格式正常、退出码 0。
**唯一能暴露它的是「工具自检」**（见 3.5.3）。

⇒ 正确顺序：**先在变异态下取快照，再还原**。

#### 3.5.2 同类隐蔽失效：恒绿陷阱的三种形态

| 形态 | 表现 | 暴露方式 |
|---|---|---|
| **快照非确定** | 基线与变异快照永远不同 ⇒ 全判盲区 | 跨进程双 seed 比对 |
| **快照覆盖不足** | 某模块的变异对快照不可见 ⇒ 全判等价 | 输出面覆盖检查 |
| **取快照时机错** | 快照取自已还原的源码 ⇒ 全判等价 | **工具自检** |

三者**症状相同**（结论不可信）但**根因不同** ⇒ 必须**逐个**排除，
不能靠"报告看起来合理"来判断。

#### 3.5.3 ★ 工具自检守卫（唯一能抓到这类错误的东西）

`tests/heluo/test_heluo_mutation_sweep_selfcheck.py`：
**故意制造一个真盲区**，验证扫描器能抓到它：

* 把守卫生效范围（`--tests`）指向一个只含**恒真用例**的临时目录
  ⇒ 没有任何守卫能抓住任何变异
  ⇒ 存活且行为改变的变异 ⇒ **必须**被判为真盲区
  ⇒ 扫描器**必须**返回退出码 **2**

⚠ 这条守卫的**基线范围也必须用隔离的临时目录**——
若用全量 `tests/heluo`，扫描器的基线跑全量时会**再次调用本守卫**
⇒ **无限套娃** ⇒ 基线红 ⇒ 极具误导性的「基线就红，先修基线」
（实测踩过）。

#### 3.5.4 由此得到的一条方法论

> **任何「测量工具」都必须有自检**。
> 测量工具坏掉时，它不会说"我坏了"，它会**给出一个看起来合理的错误答案**。
> ⇒ 工具的输出（"盲区 0"）必须由**独立的自检**来担保，
>    而不是由"跑完没报错"来担保。

## 四、用法

```bash
# 扫单个模块
python tools/heluo/mutation_sweep.py --module time_layer_judgment

# 扫全部河洛模块（1163 条变异）
python tools/heluo/mutation_sweep.py --all

# 限量（默认 120）
python tools/heluo/mutation_sweep.py --all --limit 400

# 从第 N 条开始（分批扫全量）
python tools/heluo/mutation_sweep.py --all --offset 300 --limit 300
```

进度看 `mutation_sweep.log`（**不是** stdout，管道会缓冲）。

⚠ **一次只跑一个扫描进程** —— 两个进程同时跑会互相污染
（A 还原源码时 B 正在变异）⇒ 结果全错。

⚠ **扫描期间不要提交 / 不要编辑 `src/`** —— 扫描是原地改源码的，
残留变异会让 `git status` 变脏、被 pre-push 拦下（这正好是第二道保险）。

### 4.1 ★ 已接入 CI（`.github/workflows/mutation-sweep.yml`）

分两档，理由是**时长**：

| 档 | 触发 | 内容 | 时长 | 作用 |
|---|---|---|---|---|
| **快速档** | push / PR（仅 `feature/heluo-engine-package-20261011` 分支） | `frozen_state.py` + `jiegua.py` | ~2～4 分钟 | **有真盲区 ⇒ 立刻红** |
| **全量档** | 夜间定时（UTC 18:00）+ 手动触发 | 全部 **22** 个核心模块，按 **6 个分片**并行 | ~25 分钟/分片 | 全量体检，报告留档 |

⚠ **为什么不把全量档放进 PR 门禁**：本机实测全量需 **6736 秒（约 2 小时）**
⇒ 放进 PR 门禁会让每个 PR 等两小时 ⇒ **实际会被绕过** ⇒ 比不做还糟。
⇒ 门禁用「分钟级快档」，全量用「夜间档」。

⚠ **分片是「job 级」并行，不是「进程级」并行**：
变异扫描是**原地改 `src/`** 的 ⇒ 同一 workspace 内并行会互相污染
（A 还原源码时 B 正在变异）⇒ 结果全错。
⇒ 每个分片是**独立的 GitHub job**（各自独立 checkout）⇒ 天然隔离；
同一 job 内仍然**串行**跑模块。

⚠ **CI 里的两道保险**：

1. **扫描器退出码**：有真盲区 ⇒ 退出码 **2** ⇒ job 直接红。
   ⚠ 不靠 CI 再去 grep 日志文本（文案一改 grep 就失效 ⇒ 又成恒绿陷阱）。
2. **还原校验**：扫完检查 `git diff --quiet -- src/`
   ⇒ 万一还原逻辑失效，CI 在这里红，而不是带着被污染的源码继续。

⚠ **判据依据**：CI 只认**机器可读 JSON**（`--json-out`）的稳定字段
（`blind_spots` / `restore_ok` / `baseline_ok`），不解析日志文案。

### 扫描发现的**真缺陷**

**① `_polarity_of()` 是死代码** —— 我重构后零调用。
它让变异扫描的盲区清单被噪音污染，也误导读者以为该函数在起作用。

⇒ 已删（其判据依据已迁入实际使用路径的 `detail` 文本），
并新增守卫 `tests/heluo/test_heluo_no_dead_code.py`：
包内模块级函数/类**不得零引用**。

⚠ 该守卫必须把**主仓 vendor 目录**算进引用范围 ——
本包许多函数是**跨仓公开 API**（如 `transparent_ten_gods` 主仓引用 14 次），
只看包内会被误判成死代码。
⚠ 也不能把守卫**自身**算进去（它的注释会提到被检查的名字 ⇒ 死代码被自己「洗白」）。

**② 子进程调用漏传 `env`（全量回归时暴露）**

`tests/heluo/test_heluo_cli.py :: TestNoStrayOutput::test_import_is_silent`
构造了 `env`（含 `PYTHONPATH`）却**从未传给 `subprocess.run`**：

```python
env = dict(os.environ)
env["PYTHONPATH"] = str(_REPO / "src")          # ← 构造了
p = subprocess.run([sys.executable, "-c", code], capture_output=True, ...)
                                                  # ↑ 没把 env 传进去
```

⇒ 子进程走**父进程的环境** ⇒ **同一份代码在不同环境下结论相反**：

* 本机（未 `pip install`）⇒ `heluo_engine` 不可导入 ⇒ rc=1 ⇒ **假红**；
* CI（`pip install -e .`）⇒ 包全局可导入 ⇒ rc=0 ⇒ **假绿**。

而这条测试真正要验的是「**导入引擎本身**不产生 stdout 噪声」，
不是「环境里装没装包」⇒ **被测断言从未真正生效**。

⇒ 已修（传 `env=env`），并新增守卫
`tests/heluo/test_heluo_subprocess_env.py`：
**子进程调用必须显式传 `env=`**（AST 精确到调用点的关键字实参）。

⚠ 该守卫**做过自验证**（把修复回退 ⇒ 守卫变红 ⇒ 精确指向 L234），
否则就是「恒绿陷阱」。

**③ ★ 证据文本非确定（生产缺陷，2026-10-26）**

`yuan_qi.py` 把 Python `set` 直接插值进证据文本：

```python

```

set 的字符串表示顺序依赖 **PYTHONHASHSEED**（每进程随机）
⇒ 同一盘排两次，卦名顺序就不同（如 `{'坤','巽','坎'}` vs `{'巽','坎','坤'}`）。

**双重后果**：

* **生产侧**：证据文本是**审计留痕**，不可复现的留痕无法用于回归比对；
* **工具侧**：行为快照**非确定** ⇒ 基线快照与变异快照永远不同
  ⇒ **所有存活变异都被误判成真盲区** ⇒ 盲区清单全是噪音。

⇒ 已修（一律 `sorted()` 后再拼）；同类修法见 `hua_gong.py` 的 `sorted(zhengti)`。
⇒ 守卫：`tests/heluo/test_heluo_snapshot_determinism.py`
（**跨进程**两次快照逐字段比对 —— 必须跨进程，同进程内哈希种子相同检不出来；
且**自验证**过：回退 ⇒ 守卫变红）。

**④ 快照覆盖面不足会掩盖盲区（2026-10-26）**

`frozen_state` 的 `FrozenHeluoState` 原本**完全不在快照里**
⇒ 该模块的变异让快照输出**不变** ⇒ 被误判成「等价变异」
⇒ **真盲区被静默掩盖**。

⇒ 快照已扩到 `HeluoResult` **全部主要输出面**；
守卫同文件：`test_snapshot_covers_main_output_surfaces`（缺哪个输出面直接点名）。

**⑤ 扫描器快筛无视 `--tests` 范围（2026-10-26）**

快筛硬编码 `tests/heluo` ⇒ 当 `--tests` 指向别处时，
「这个范围内有没有守卫」这个问题被**范围外**的守卫回答了
⇒ 结论与「守卫生效范围」这个前提**不一致**。

⇒ 已改为快筛与慢筛用**同一个** tests_dir。

**⑥ 扫描中断会残留变异（2026-10-26 加固）**

扫描是**原地改 `src/`** 的 ⇒ 被 Ctrl-C / 被杀 / 抛异常 ⇒ 源码**残留变异**，
而残留的变异可能恰好让测试绿 ⇒ **下一个使用者拿到的是被污染的源码**。

实测踩过：手动取消扫描后 `time_layer_judgment._yao_ci_from_guajie`
残留了 `return None`（原为 `return ("", "")`）⇒ 靠 `git diff` 才抓到。

⇒ 已加 `finally` + 信号处理器（SIGINT / SIGTERM / SIGBREAK）**无条件还原**
并二次校验哈希。

**⑦ ★★★ 扫描器致命顺序错误（2026-10-26，最严重的一处）**

详见 3.5.1。一句话：

```python
runner.restore()                            # 先还原源码
mut_snap = _behaviour_snapshot(cache)       # 后取快照（读到的已是原码）
```

⇒ 快照**必然**等于基线 ⇒ **每个存活变异都判成「等价」**
⇒ **真盲区一个都发现不了**，而报告写「★ 真盲区 0」。

⚠ 它**不报错、不崩、退出码 0、还原校验通过** ⇒ 两轮扫描都没发现它。
⇒ 唯一能暴露它的是**工具自检守卫**
（`test_heluo_mutation_sweep_selfcheck.py`：故意造一个真盲区，
验证扫描器能抓到且退出码为 2）。

⇒ **这是本轮最重要的教训**，也是下面 6.4 那条方法论的由来。

**⑧ 固定 seed 会让确定性守卫恒绿（2026-10-26）**

确定性守卫原本「跨进程跑两次比对」⇒ 依赖「两次进程拿到**不同** seed」。
若环境固定了 `PYTHONHASHSEED=0`（很多 CI 会这么做）⇒
两次拿到**同一** seed ⇒ **非确定性检不出来** ⇒ 守卫恒绿。

实测：把 seed 固定为 0 后，即使源码里有 set 插值，守卫仍然**全绿**。

⇒ 修法：守卫**显式用两个不同的 seed**（"0" 与 "1"）跑自己的子进程
⇒ 无论外部环境如何设，都必然能暴露 set/dict 顺序依赖。

⇒ 同时：扫描器自己的快照对比**必须固定同一个 seed**
（否则基线与变异快照在任意 set 插值处都不同 ⇒ 全判盲区）。

## 六、这套方法能回答什么、不能回答什么

### 6.1 一句话结论

> **「一次跑出全部缺陷」做不到；但「一次跑出某一类缺陷的全部」可以做到。**
>
> 本仓的做法是把缺陷空间**切成互不重叠的几类**，每类配一个**可穷尽**的手段：
> 变异测试负责「代码层错误」，静态守卫负责「守卫自身的失效」，
> 具名守卫负责「原典语义」。
> ⇒ 任何新缺陷出现时，都应该能**立刻归到某一类**，并被对应手段**当场抓住**。

### 6.2 对照表：谁能抓、谁抓不到

| 缺陷类别 | 例子 | 手段 | 可穷尽？ |
|---|---|---|---|
| **代码层错误**（四类算子） | 阈值写错、比较反了、返回值被吞、否定漏了 | ★ **变异测试**（本仓 22 模块 / 522 条已扫） | ✅ **可**（自动生成 + 全量守卫验证） |
| **守卫自身失效** | 同名测试方法覆盖、环境依赖导致的假绿/假红、死代码 | **AST 静态守卫**（同名检测 / env 检测 / 死代码检测） | ✅ **可**（静态可判定） |
| **原典语义错误** | 判据引了《河洛理数》另一句意思相近的话；吉凶门槛取错 | **具名守卫**（判据须附原典出处、逐字可回查） | ⚠ **部分**（靠人查证，但**必须留出处**才能查） |
| **逻辑错误** | 条件组合错、优先级错、分支漏一种情况 | 人工 + 代码评审 | ❌ **不可穷尽** |
| **并发错误** | 共享状态、竞态 | 人工 + 并发测试 | ❌ **不可穷尽** |
| **性能问题** | 复杂度退化、慢路径 | 人工 + 性能基准 | ❌ **不可穷尽** |
| **需求理解错** | 判据本身选错方向（不是"引错句"，是"用错思路"） | 人工 + 原典研读 | ❌ **不可穷尽** |

### 6.3 ⚠ 为什么「真盲区 = 0」不能过度解读

本轮 522 条变异、**真盲区 0**，它**只**证明：

> 在「四类算子能表达的错误」这一范围内，
> **判据核心层的每一次行为改变都会被至少一个守卫发现**。

它**不**证明：

* ❌ 判据引用的原典句是对的（要靠具名守卫 + 逐字回查）；
* ❌ 判据的思路是对的（要靠人工研读原典）；
* ❌ 非算子覆盖的错误不存在（逻辑/并发/性能/需求理解）。

⇒ **变异测试是「守卫有效性的体检」，不是「代码正确性的证明」。**

### 6.4 扫描的**可重复性**（这才是"一次跑出来"的关键）

* 变异**自动生成**（AST）⇒ 不依赖人的直觉 ⇒ **不会因为"这次没想到"而漏**；
* 变异**可枚举**（有 `--offset` / `--limit`）⇒ 全部 1163 条可**分批跑完**；
* 每个结论都带**还原哈希校验** ⇒ 源码没被污染；
* 存活变异用**行为快照**定性 ⇒ 不把"等价变异"误报成缺陷，也不放过真盲区；
* ★ **工具本身有自检**（`test_heluo_mutation_sweep_selfcheck.py`）
  ⇒ 保证"盲区 0"这个结论不是工具坏了导致的假象。

⇒ 换句话说：**「一次跑出全部」做不到，但「一次跑完、可复现、不遗漏已注入的缺陷」做到了。**
   剩下的缺口是**算子覆盖不到的那些类**，由 6.2 表里对应的其他手段兜。

### 6.4.1 ★★ 本轮最可迁移的一条教训

> **测量工具坏掉时，不会说"我坏了"，它会给出一个看起来合理的错误答案。**
>
> 实测：扫描器有个「先还原、后取快照」的两行顺序错误 ⇒
> 报告连着两轮都写「★ 真盲区 0」——
> **不报错、不崩、退出码 0、还原校验通过、日志格式正常**，
> 看起来比什么都可信，而它**根本没在测**。

⇒ **由此得到三条硬规则**：

1. **测量工具必须有自检**：故意造一个它该抓到的东西，验证它真能抓到
   （本仓：故意造真盲区 ⇒ 扫描器必须报出来且退出码为 2）。
2. **不要用"跑完没报错"当结论正确的证据** ——
   还原校验通过 ≠ 结论正确（它只证明"没污染源码"）。
3. **结论必须能证伪**：任何"0 缺陷 / 0 盲区"的报告，
   都要能回答「**如果这里真有缺陷，这套工具能发现吗？**」
   —— 答不上来，这个 0 就**没有意义**。

⇒ 这条不止适用于变异测试：
**任何自动化检查（覆盖率报告、静态检查、快照对比、契约测试）都可能给出假绿**，
都需要一条「**它能发现真问题吗**」的自检。

### 6.5 建议的常态化用法

```bash
# 每次改了判据层 → 跑对应模块（分钟级）
python tools/heluo/mutation_sweep.py --module hua_gong

# 每个里程碑 → 跑核心 22 模块（约 2 小时）
python tools/heluo/mutation_sweep.py --module hua_gong.py   # 逐模块，见 tools/heluo/ 的批跑说明

# 全量 1163 条 → 分批
python tools/heluo/mutation_sweep.py --all --offset 0 --limit 400
python tools/heluo/mutation_sweep.py --all --offset 400 --limit 400
python tools/heluo/mutation_sweep.py --all --offset 800 --limit 400
```

⇒ 判据层**每次改动**都跑一遍 ⇒ 缺陷不必等到"全量回归才发现"，
   而是**改完当场就知道有没有守卫盲区**。
