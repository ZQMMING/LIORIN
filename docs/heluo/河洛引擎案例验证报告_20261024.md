## 1. 验证方法

### 1.1 为什么命例能当验收基准

命例的四柱是**真实命例已排定的**（由实战者排出并公开），不是引擎自己算的。
引擎用**自己的**历法/节气/时柱链从公历重算 ⇒ 四柱一致率直接度量地基正确性，
且**表结构、接口形状、变异演练全都发现不了**这类错误。

### 1.2 反查公历（干支 → 日期/时辰）

四柱在 **60 年内重复** ⇒ 需消歧：

1. 建索引：遍历 1900–2100 共 73,414 天，按 (年柱, 月柱, 日柱) 与 (…, 时柱) 建表；
2. 以命例四柱查表得候选年份；
3. **消歧**（两级）：
   - 从 `jobInfo` / `caseDetail` 提取**人生事件年**（如「2011年入选」「2023年升任」），
     命主当年至少 16 岁 ⇒ `birth_year ≤ min(事件年) − 16`；
     取满足约束的**最晚**候选年 ⇒ 1031 例；
   - 无事件年线索者，取**不超过 2025 的最晚**候选年（当代命例库）⇒ 627 例；
   - 两者皆不满足 ⇒ 23 例（落在 2098–2100，判定为**反查不可靠，不计入验证**）。

### 1.3 两条路径的口径（关键）

| 路径 | 走哪条链 | 真太阳时 |
|---|---|---|
| **A** | `HeluoAdapter.compute()` → `BaziEngine` | **不做**（独立入口无出生地参数） |
| **B** | `HeluoAdapter.compute_from_context()` → `TimeResolver` | **做**（经度 + 均时差） |

**路径A 才是「标准时」口径**：公开命例的四柱多按北京时间（东经 120）排定，
故路径A 的可复现率才是与命例的同口径比较。

**路径B 另有取样口径**：命例只给**时柱**（2 小时区间），不给具体时刻 ⇒
路径B 遍历该时柱区间 ±1 小时 × 前一天/后一天，只要**存在**一个使四柱全对的解即算可复现。

## 3. 本轮修复：出生地解析（真太阳时的前提）

### 3.1 问题

真太阳时要靠出生地**经度**（1° 经度 = 4 分钟真太阳时）。
现实中传入的是「河北省唐山市」这类**行政地址**。

**修复前**：包内 `locations.json` 793 条（中国 201），`lookup()` 只做**精确匹配**
⇒ 1681 例里只有 **642 例（38.2%）**能解析到地点，其余 1039 例落到默认经度
⇒ **真太阳时在 62% 的真实场景下用不上正确经度**。

### 3.2 修法（三处）

**① 地点表扩充**：合并 `chinese-fortune-bazi/assets/cities_cn.json`
（**376 个中国城市**，三路独立编制〔按省份 / 按行政区划代码 / 按拼音〕取一致值，
争议项经度差 ≤0.25° 即 ≤1 分钟真太阳时，取中位数；精度说明原文：
「1° 经度 = 4 分钟真太阳时；本表精度 ≤0.25°（≤1 分钟），**时辰边界判定足够**」）。
- 源表 `not_included` 列出的 **26 项单源未核城市不加入**（不把未核数据写进包里）；
- 补 **26 个省级兜底条目**（`CN_PROV_*`，取省会/首府坐标）供「XX省」这类只有省名的地址；
- **不把省名放进城市 alias** —— 省名不是该城市的别名，
  否则「湖北」会精确命中最后一个写入的湖北城市（仙桃/十堰…），省级条目反而被挤掉；
- 结果：**793 → 1078** 条。

**② 行政地址解析**（`location_registry._resolve_in_text`）：精确未命中时降级为
地址文本子串匹配，排序规则：
1. **出现位置越靠右越优先** —— 行政地址最后一段才是实际出生地
   （「黑龙江省大庆市」⇒ 大庆；「浙江省绍兴市嵊州市」⇒ 嵊州市）；
2. 同结束位置取更长匹配；
3. **省级兜底最后** —— 省会坐标与真实城市可差 1–2°（真太阳时 4–8 分钟），足以改变时柱。

**③ 性能**：子串匹配若每次扫全部 1000+ 条目 × 别名，批量排盘时是 O(3000)。
改用**别名首 2 字索引**（`_alias_prefix2`）取候选 ⇒ 单次 lookup **0.05 ms**
（1000 次热查 4 ms）。

### 3.3 修复前后

| | 修复前 | 修复后 |
|---|---|---|
| 地点表条目 | 793 | **1078** |
| 1681 例地址解析命中 | 642（38.2%） | **1660（98.75%）** |
| 21 个抽样地址 | 多数落到「北京」 | **21/21 全部解析到具体城市** |

例：「新疆维吾尔自治区乌鲁木齐市」→ 乌鲁木齐（**87.62°**，真太阳时比东经 120 早 **129.5 分钟**）

## 4. 路径B 的 53 例差异：归因（**不是引擎缺陷**）

对 53 例逐例诊断：

| 证据 | 数值 |
|---|---|
| **经度偏移为负（西部/时区偏）** | **52 / 53**（最大 **-135.4 分钟**） |
| 期望时支属 **亥/子/丑**（子时及其相邻） | **29 / 53** |
| 落到省级兜底（该城市不在表内） | 28 / 53 |

**机制**：河洛引擎按**真太阳时**定时辰；公开命例多按**标准时**排。
西部城市经度偏 60–135 分钟 ⇒ 足以把时辰整体前移 1–2 个时辰
（子时 00:00 尤其敏感：真太阳时推到前一天 23:xx ⇒ 时柱退到亥时，
并因「夜子时换日」规则连**日柱**一起变）。

**这是口径差，不是错误**：
- 河洛按真太阳时 + 节气，与《河洛真数》「生于二月至八月以前者得时也」这类
  以节气/时辰立论的原典口径一致；
- 当代命书多用北京时间（东经 120），故两者在西部必然出现时辰差。
- 引擎行为与主仓 AGENTS.md 冻结清单「子初（晚子时）换日规则（B-02 已锚定）」一致。

⇒ **不应**为了让数字好看而关掉真太阳时；正确处置是**把出生地解析做准**（§3 已做）。

## 6. 口径与局限（诚实声明）

1. **标准时口径是主结论**：路径A 100% 复现证明的是**历法/节气/时柱链**正确；
   它**不**证明真太阳时口径与命例一致（那是口径差，§4）。
2. **反查本身有不确定**：60 年一轮的干支 + 缺失的事件年线索 ⇒ 23 例落在 2098–2100，
   判为反查不可靠，已剔除；其余按 §1.2 两级消歧。
3. **命例本身的四柱可能有误**：公开反馈由不同实战者排出，理论上可能有个别错例；
   本报告只报告「引擎能否复现命例」，不裁定「命例是否正确」。
4. **未覆盖**：真太阳时口径的**期望值**没有独立基准（需真实出生时刻，
   命例未提供）⇒ 路径B 只能验证「存在候选解」，不能验证「唯一解」。
