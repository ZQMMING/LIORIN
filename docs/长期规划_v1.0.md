## 二、长期方向一：十干级精度

### 2.1 当前状态

| 维度 | 状态 |
|------|------|
| 当前精度 | 五行级（木火土金水） |
| 目标精度 | 十干级（甲乙丙丁戊己庚辛壬癸） |
| 原型尝试 | V1：44.0%，失败 |
| 失败原因 | 只做了调候的天干级，扶抑轨还是五行级，两套精度不一致 |

### 2.2 为什么需要十干级

五行级判断的问题：壬癸不分、庚辛不分。例如：
- 癸亥大运：壬水和癸水都是"水"，但壬水是阳水（泛滥），癸水是阴水（滋润），喜忌可能不同
- 庚申大运：庚金和辛金都是"金"，但庚金是阳金（刚健），辛金是阴金（珠玉），喜忌可能不同

原著中大量论述是十干级的（如《穷通宝鉴》"五月壬水，取庚为用取癸为佐"），五行级判断无法精确覆盖。

### 2.3 前置条件

启动十干级精度需要以下前置条件：

| 前置条件 | 说明 | 当前状态 |
|----------|------|----------|
| 全轨道十干级 | 不只调候，所有轨道（格局/病药/体用）都要十干级 | ❌ 只有调候部分十干级 |
| 数据源统一 | 用Authority Matrix确认各轨的天干来源 | ✅ Authority Matrix v0.2已完成 |
| 十干用神候选 | 用神引擎输出从"五行级"升级到"十干级" | ❌ 当前是五行级 |
| 十干fav/avoid集合 | fav/avoid集合从"五行"改为"天干" | ❌ 当前是五行级 |
| 分轨验证 | 每个轨的十干级独立验证 | ❌ 未做 |

### 2.4 改动范围

| 模块 | 改动内容 | 风险 |
|------|----------|------|
| yongshen_engine.py | 用神候选从五行级升级到十干级 | 高（核心模块） |
| dayun_align.py | fav/avoid集合从五行改为天干 | 高（生产链路） |
| dayun_xiji.py | 大运喜忌判断从五行级升级到十干级 | 中 |
| climate_structure.py | 调候候选已经是十干级，需统一接口 | 低 |
| bingyao_layer.py | 病药候选从五行级升级到十干级 | 中 |
| special_pattern.py | 从格/专旺格判断从五行级升级到十干级 | 中 |

### 2.5 预期收益

| 阶段 | 单一对齐率预期 | 说明 |
|------|----------------|------|
| 当前（五行级） | 79.0% | 基线 |
| 十干级（调候+扶抑） | 80%–82% | 十干级能区分壬癸/庚辛 |
| 十干级（全轨道） | 82%–85% | 所有轨道十干级 |

预期收益：+3–6pp。但需要根本性架构重构，不是增量优化。

### 2.6 风险

| 风险 | 说明 | 应对 |
|------|------|------|
| 对齐率短期下降 | 十干级精度更高，但可能误判更多案例 | 先小样本验证，再全量切换 |
| 两套精度不一致 | 部分轨道十干级，部分五行级，导致判断冲突 | 全轨道同时升级，不做半升级 |
| 用神候选爆炸 | 十干级候选比五行级多，可能导致fav集合过大 | 严格控制候选数量，保留优先级 |
| 回归风险 | 核心模块改动大，可能影响79.0%基线 | 保留五行级作为fallback，逐步切换 |

### 2.7 决策条件

启动十干级精度的条件：

1. **有明确的十干级案例需求**：用户或产品需要区分壬癸/庚辛的喜忌
2. **五行级已接近上限**：当前79.0%，如果通过其他优化无法突破80%，考虑十干级
3. **有足够的开发周期**：十干级需要全轨道升级，预计2–4周
4. **有独立验证集**：非DTS验证集建立后，可以验证十干级的真实效果

不满足以上条件时，不启动十干级。

## 三、长期方向二：四轨并行重试

### 3.1 当前状态

| 维度 | 状态 |
|------|------|
| 当前架构 | 用神四轨合并计算（格局/调候/病药/体用） |
| 目标架构 | 四轨独立输出，按优先级裁决 |
| 原型尝试 | V1：57.7%，V2：55.3%，V3：58.2%，全部失败 |
| 失败原因 | 数据源不统一，强行分开反而损失精度 |

### 3.2 为什么需要四轨并行

当前用神引擎是合并计算，无法区分各轨的独立判断。四轨并行的价值：

1. **可解释性**：每个结论标注来源轨道（格局/调候/病药/体用）
2. **冲突保留**：各轨判断冲突时，输出多解，不强行裁决
3. **优先级裁决**：按原著优先级规则裁决（冬夏调候优先，非冬夏格局优先）
4. **Authority Matrix支撑**：旺衰/格局/用神三部以上各有独立体系，多轨并行有原著依据

### 3.3 前置条件

启动四轨并行需要以下前置条件：

| 前置条件 | 说明 | 当前状态 |
|----------|------|----------|
| 数据源统一 | 各轨使用统一的底层数据（wang_shuai/qiang_ruo/tier2） | ✅ V7.x已完成 |
| 各轨独立接口 | 每轨有独立的输入输出定义 | ❌ 当前是合并计算 |
| 优先级裁决规则 | 按原著优先级规则裁决（冬夏调候优先等） | ⚠️ 部分有，需完善 |
| 冲突保留输出 | 各轨冲突时输出多解 | ✅ V7.18已完成 |
| 分轨验证 | 每个轨的独立验证 | ❌ 未做 |

### 3.4 改动范围

| 模块 | 改动内容 | 风险 |
|------|----------|------|
| yongshen_engine.py | 从合并计算改为四轨独立输出 | 高（核心模块） |
| dayun_align.py | 消费四轨独立输出，按优先级裁决 | 高（生产链路） |
| dayun_xiji.py | 消费四轨独立输出 | 中 |
| Authority Matrix | 完善各轨的优先级裁决规则 | 低 |
| 前端展示 | 展示各轨独立判断+冲突标注 | 中 |

### 3.5 预期收益

| 阶段 | 单一对齐率预期 | 说明 |
|------|----------------|------|
| 当前（合并计算） | 79.0% | 基线 |
| 四轨独立输出（不裁决） | 78%–79% | 可能短期下降 |
| 四轨+优先级裁决 | 79%–81% | 裁决正确时提升 |
| 四轨+冲突保留 | 命中率@K提升 | 单一对齐率可能不变 |

预期收益：+0–2pp。四轨并行的主要价值是可解释性和冲突保留，不是单一对齐率提升。

### 3.6 风险

| 风险 | 说明 | 应对 |
|------|------|------|
| 对齐率下降 | 四轨独立输出可能损失合并计算的精度 | 保留合并计算作为fallback |
| 裁决规则复杂 | 优先级裁决规则需要从原著推导，可能有边界 | 先做简单裁决，逐步完善 |
| 回归风险 | 核心模块改动大 | 小样本验证，逐步切换 |
| 收益不确定 | 四轨并行的主要价值是可解释性，不是对齐率 | 明确目标，不追求对齐率提升 |

### 3.7 决策条件

启动四轨并行的条件：

1. **有明确的可解释性需求**：用户或产品需要知道每个结论的来源轨道
2. **有冲突保留的产品需求**：用户需要看到多解输出，不是单一结论
3. **数据源已统一**：V7.x已完成数据源统一，这是前置条件
4. **有足够的开发周期**：四轨并行需要核心模块重构，预计2–3周

不满足以上条件时，不启动四轨并行。

## 六、决策框架

### 6.1 什么时候启动长期项目

| 条件 | 十干级 | 四轨并行 |
|------|--------|----------|
| 有明确的产品需求 | ✅ 必须 | ✅ 必须 |
| 五行级/合并计算已接近上限 | ✅ 建议 | ⚠️ 可选 |
| 有足够的开发周期（2–4周） | ✅ 必须 | ✅ 必须 |
| 有独立验证集 | ⚠️ 建议 | ⚠️ 建议 |
| 数据源已统一 | ✅ 已完成 | ✅ 已完成 |

### 6.2 什么时候不启动

- 当前基线稳定（79.0%+98.2%），无明确产品需求
- 开发周期不足（<2周）
- 没有独立验证集，无法验证真实效果
- 只是为了"追数字"而启动

### 6.3 启动后的执行原则

1. **小样本验证先行**：先用20–30例验证方向，再决定是否全量
2. **保留fallback**：保留当前架构作为fallback，逐步切换
3. **不追求短期对齐率**：长期项目可能短期对齐率下降，不要回退
4. **可解释性优先**：十干级和四轨并行的主要价值是可解释性，不是对齐率
5. **原著优先**：所有规则从原著推导，不做案例拟合
